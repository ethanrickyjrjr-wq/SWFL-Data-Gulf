## 2. The stack — fresh choices, each justified at our volume (Rule 11)

- **Ingest: Python + dlt → DuckDB file.** dlt verified live in-session (v1.29.1, dlthub.com/docs):
  schema inference, incremental merge, **schema contracts** (freeze/evolve — a vendor-shape-drift
  guard we hand-rolled in brain-platform), REST/filesystem sources. The lake is a single gitignored
  `.duckdb` file — zero infra, zero egress, zero network attack surface. This deletes the entire
  egress/billing failure class from the proof (playbook §4.5–4.6) instead of guarding it.
- **Brains: deterministic SQL + typed JSON output.** A brain = one module that reads ONLY the lake,
  computes numbers in code (never LLM math), and emits `BrainOutput`: every figure is
  `{value, source_url, as_of, method}` — provenance as a TYPE, not a convention. LLM (if used at
  all in v1) writes prose over precomputed facts only, behind a no-invention lint.
- **Master or not:** with 1–2 brains there is nothing to synthesize — the email binds directly to
  leaf brain outputs. No master tier in the proof. Add a combiner brain only if the email layout
  needs two domains merged into one narrative block. (Answers the operator's open question.)
- **Email: react-email, coded-grid recipes only.** Verified live in-session (react.email/docs):
  Row/Column/Section/Container components, `@react-email/render` to HTML, Resend integration
  (our existing sender). The layout is a coded recipe — certain data binds to certain slots; the
  AI never free-authors layout (operator decree 08/01). This replaces brain-platform's three
  hand-rolled render engines with one maintained library. **Bind, don't prompt** — our own
  competitor research (Gamma, 07/30) shows prompted charts/values are non-deterministic; every
  slot in our template is a typed binding to a BrainOutput field.
- **Orchestration: none.** Four fetchers + one build script, run manually or by one cron later.
  No workflow trees (playbook §4.7 — consolidation created an undefended SPOF last time).

## 3. What is deliberately DIFFERENT from brain-platform

1. **Lake = local DuckDB, not Supabase.** At proof volume a cloud Postgres is pure liability
   (egress, RLS, network probes — all documented incidents). Graduation to hosted comes later, as
   a decision, if the proof earns it.
2. **The source registry is DERIVED from pipeline code, not hand-typed.** Playbook §4.16: an
   assertion that can be computed must never be typed. `registry.json` is generated by
   introspecting the pipelines (name, fields pulled, ceiling, consumer) and a test fails if a
   pipeline exists without a registry entry or a registry entry without a consumer. Recording half
   and acting half ship in the same mechanism by construction (§1, §4.3).
3. **One recipe registry.** Not two (the 08/01 "thanks for the fucking confusion" two-registry
   gripe). A recipe = layout + slot bindings + voice, one file, one type.
4. **End-to-end test IS the definition of done** (the voice-picker lesson, 08/01–08/02): one
   integration test runs source-fixture → lake → brain → rendered HTML and asserts a known
   sourced number AND its citation appear in the final artifact. Unit-green is not done.
5. **No-invention lint runs on the RENDERED artifact** (playbook §4.4 — grep the rendered string,
   not the helper): every numeral in the output HTML must trace to a BrainOutput fact or be
   whitelisted (dates, layout constants). Fails the build, not a warning.
6. **Source reliability is the selection criterion** (operator correction 08/02: "you just stated
   plenty that always fail"). Official, versioned, documented APIs only — no scraped portals, PDF
   extractions, third-party mirrors, or state SFTP drops in the proof's 4. Free registered keys
   are acceptable (FRED-class); paid or approval-gated access is out. Keys live in an ignored
   `.env` with a scan hook from commit zero (07/18 plaintext-dump incident).

## 5. Pipeline flow (the proof, end to end)

```
4 fetchers (heterogeneous: API JSON / bulk CSV / ArcGIS REST / crawl)   [scout-verified sources]
   → dlt load → lake.duckdb  (merge keys, schema contracts, row-count floor before any replace)
   → brain(s): SQL → BrainOutput JSON {value, source_url, as_of, method} + freshness token
   → email build: coded react-email recipe binds slots to BrainOutput fields
   → render HTML (+ screenshot) → no-invention lint on rendered HTML → e2e test green
```

Output of the proof: one produced email (HTML file + preview screenshot) a real buyer in the
chosen industry would want, every number traceable to a live public source.

## 6. Failure modes → typed guards (RULE 3.5, none hand-waved)

| Failure | Guard (typed) |
|---|---|
| Source changes shape silently | dlt schema contract (freeze on unexpected column) + fixture test — validation |
| Empty/partial pull destroys good data | row-count floor + non-null key guard before merge — gate |
| Pipeline exists, nothing consumes it | derived registry + consumer test — test |
| LLM invents a number in prose | no-invention lint on RENDERED HTML — lint |
| Unit-green while wiring is dead | e2e source→email integration test — test |
| Hook that never fires (exit-1 no-op, unregistered) | meta-guard test + exit-2 discipline — test |
| Freshness read from job status | detector on MAX(loaded_at) in lake — detector |
| Hand-typed claims drift (counts, field lists) | registry derived from code; computed, never typed — gate |
| "We don't have X" while the source holds it | ceiling recorded per source at ingest, auto-surfaced — validation |
| Secrets leak | no credentials in v1; ignore + scan from commit zero — lint |
